# Claude Code 제작 요청 프롬프트 — 하이테크본부 가을운동회 모바일 웹앱

> 사용법: 이 파일 전체를 Claude Code에 전달하고, `01_event_summary.md` 및 `assets/`를 프로젝트에서 읽을 수 있게 제공한다. 이 파일은 제작을 요청하기 위한 기획서이며 구현 결과물이 아니다.

---

당신은 이 프로젝트의 시니어 풀스택 개발자이자 제품 디자이너다. 아래 요구사항을 실제 행사에서 여러 사람이 동시에 사용하는 완성도 높은 모바일 웹앱으로 구현하라. 화면 목업으로 끝내지 말고, 영속 DB·서버 인증·실시간 채팅·관리자 점수 관리까지 동작하게 만든다. 기존 저장소가 있다면 먼저 구조와 지침을 읽고 적합한 기술을 유지하라. 아래 명시한 규칙은 임의 변경하지 않는다.

## A. 제품 목표와 작업 범위

2026년 10월 21일 하이테크본부 가을운동회 현장 도구다. 참가자는 QR로 웹주소에 접속해 이름·사번을 입력한다. 사전 명단과 일치하면 자신의 조와 행운권을 확인하고 일정·지도·전체채팅·팀채팅을 이용한다. 지정 관리자만 8개 조 점수판, 점수 부여·취소·감사 로그를 이용한다.

최우선 요구사항:
1. 이름과 사번은 사전에 등록된 동일 명단 행과 일치해야 한다.
2. 조는 사전 배정값을 표시한다. 랜덤 조 편성이나 참가자의 조 변경은 금지한다.
3. 첫 300명의 서로 다른 최초 로그인 성공자에게 1~300을 중복 없이 랜덤 배정한다. 301번째부터 301, 302, 303… 순서대로 배정한다.
4. 재로그인·새로고침·재접속·다중 기기 로그인으로 행운권이 바뀌거나 중복 생성되지 않는다.
5. 지정 관리자 로그인 시 화면 하단에 `관리자 화면` 버튼이 나타난다.
6. 관리자만 점수·순위·점수내역을 조회한다. 참가자에게 팀 점수도 공개하지 않는다.
7. 점수 부여 흐름은 `조 선택 → 종목 선택 → 점수 선택 → 사유 확인 → 최종 확인`이다.
8. 취소 시 비밀번호는 **1234**이며, 관리자 권한과 함께 검증한다.
9. 누가 어느 조에 몇 점을 어떤 이유로 줬고 누가 취소했는지 기록한다.
10. QR 이미지 생성·QR 제작 기능은 범위 밖이다. 운영자가 배포 후 URL을 QR로 만든다. 배포 가능한 소스와 설명서는 제공하되 외부 서비스 배포는 별도 요청이 없으면 실행하지 않는다.

정책 우선순위: 이 프롬프트의 사용자 확정 요구사항 > 행사 요약의 원문 정보 > 개발자 기본값. 미정 경기 규칙을 추측해 자동채점하지 말라.

## C. 사용자와 권한

역할은 `participant`, `admin`, `owner`로 구성한다.
- participant: 본인 정보·행운권·자기 조 정보·공개 안내·전체 채팅·자기 팀 채팅.
- admin: participant 기능 + 점수판·점수 부여·취소·점수 로그·공지/일정 관리·채팅 신고 처리·체크인 현황.
- owner: admin 기능 + 사전 명단 업로드·관리자 지정/해제·행사 설정·내보내기.
- owner는 제안하는 운영 역할이다. 목적은 명단/관리자 권한 변경을 통제하는 것이며 일반 관리자도 정상적으로 점수 취소할 수 있어야 한다.
- 초기 owner는 서버 초기화 명령 또는 서버 환경 설정의 사번으로 지정한다. 클라이언트 로그인 입력값으로 관리자 역할을 만들지 않는다.
- 이름·사번이 일치해도 roster가 inactive면 로그인 불가.
- 미등록 사용자의 회원가입·관리자 신청·임의 사번 추가 기능은 만들지 않는다.
- 사용자가 입력하거나 localStorage에 조작한 role/team_id를 신뢰하지 않는다.
- 역할 변경은 기존 세션에도 서버 요청부터 반영한다. 권한을 잃은 관리자에게 열린 점수 화면·구독도 더 이상 데이터가 오지 않아야 한다.

### 참가자에게 금지된 정보

전체 점수, 본인 조 점수, 상대 조 점수, 순위, 점수 증감 알림, 점수 로그, 점수 그래프, 점수 포함 CSV, 전체 명단의 사번, 타 팀 채팅.

화면에서 감추는 것으로 끝내지 않는다. API·DB 접근정책·WebSocket/실시간 채널·서버 렌더링 결과·캐시·오류 메시지·다운로드 모두 제한한다. 참가자 공용 API 응답에는 score/rank/history 필드 자체를 보내지 않는다. DOM·숨김 컴포넌트·클라이언트 상태에도 저장하지 않는다.

단, 자유 채팅에서 누군가 직접 점수를 타이핑하는 것까지 시스템이 완벽하게 막을 수 있다고 주장하지 말라. 시스템이 점수를 자동 노출하지 않게 하고, 관리자에게 점수는 관리자 화면에서만 확인하도록 안내한다. 공개 우승 발표 기능이나 점수 공개 토글은 만들지 않는다.

## D. 로그인·사전 명단

### 화면

이름, 사번 두 입력창과 `입장하기` 버튼. 자동완성으로 다른 사람 명단을 노출하지 않는다. 사번은 숫자가 아니라 문자열로 저장해 앞자리 0을 보존한다. 임의로 숫자만 허용하거나 길이를 고정하지 않는다.

### 입력 검증

- 이름: 앞뒤 공백 제거, 유니코드 NFC 정규화. 이름 내부 공백 임의 제거·유사 이름 매칭 금지.
- 사번: 앞뒤 공백 제거. 문자 대소문자 규칙은 원본 명단 기준으로 명시하고 일관 적용. 기본은 정확히 일치.
- 반드시 같은 명단 행의 이름+사번 조합을 검사한다.
- 실패 문구: `이름과 사번을 확인해 주세요. 계속 안 되면 운영진에게 문의해 주세요.` 이름 존재 여부와 사번 존재 여부를 따로 알려주지 않는다.
- 실패 반복 제한과 적절한 대기 안내. 행사장 공용 Wi-Fi 특성상 IP 하나만 기준으로 전원 차단하지 않도록 IP+계정 후보 등을 조합한다.
- 세션은 서버 검증 가능한 Secure/HttpOnly 쿠키 등 동등한 안전성을 갖춘 방법 사용. CSRF·XSS·세션 만료 처리.
- 이름+사번 방식은 사용자 지정의 간편 인증이며 강한 본인확인이 아니라는 한계를 운영 설명서에 짧게 남긴다. 임의 OTP/SMS 절차를 추가하지 않는다.
- 최초 로그인 성공을 체크인으로 기록한다. 잘못된 요청·실패·명단 업로드만으로 체크인하지 않는다.

### 명단 업로드

owner가 CSV 업로드. 예시 열: `employee_id,name,team_number,role,active`.
- 제공하는 샘플은 TEST-0001 등 명확한 가상 명단 8~16명, 관리자 포함. 실제 이름·사번을 만들어내지 않는다.
- UTF-8 BOM 및 Excel에서 저장한 CSV를 고려한다. 이름·사번을 공개 저장소나 프론트 정적 JSON에 배포하지 않는다.
- preview → 오류 검증 → 확정. 조 1~8, 역할 허용값, 사번 중복, 빈값, 잘못된 활성값 검증.
- 중복 이름은 허용하되 사번은 행사 내 유일. 오류 행은 번호·이유를 보여주고 기본은 전체 반영 중단으로 부분 적용 혼란 방지.
- 기존 체크인자의 행운권·로그는 재업로드로 초기화하지 않는다.
- 기존 명단 병합 정책을 명시하고 역할 변경은 별도 확인. 자신 또는 마지막 owner 제거 금지.
- 체크인 후 조 변경은 기본 제한. owner가 예외 변경하면 이전/이후 조, 사유, 시각을 감사 로그에 남기고 팀 채팅 권한을 즉시 갱신한다.
- 관리자 화면에 체크인/미체크인·조별 인원 현황. 참가자에게 전체 명단이나 타인 사번은 반환하지 않는다.

## E. 행운권 — 동시성까지 완결

행운권 번호는 사람마다 행사 내 하나이고 재로그인해도 영구 유지한다.

### 정확한 정책

1. 신규로 체크인한 고유 참가자에게 서버가 순번 checkin_sequence를 부여한다.
2. sequence 1~300: 아직 사용되지 않은 1~300 중 하나를 랜덤 배정한다.
3. sequence 301 이상: ticket_number = checkin_sequence. 예: 301번째 → 301.
4. 관리자도 사전 명단에 등록된 참가자로 로그인하면 동일하게 번호를 받는다. 시스템 owner 초기화나 관리용 명단 업로드는 참가자 체크인으로 세지 않는다.
5. 번호는 직원번호·조·업로드 순서와 무관하다.
6. 로그아웃·비활성화·계정 수정으로 번호를 회수하거나 다른 참가자에게 재사용하지 않는다.
7. 한 사람의 여러 브라우저 동시 로그인도 하나의 체크인과 번호만 생성한다.
8. 번호 배정 실패 시 체크인·카운터 증가도 함께 롤백한다.

### 구현 원칙

- 클라이언트 Math.random, localStorage, 단순 COUNT()+1, 서버 인스턴스 메모리만으로 구현 금지.
- 영속 관계형 DB의 트랜잭션, 행사 단위 할당 잠금/동등한 원자성, unique 제약 사용.
- `(event_id, participant_id)`와 `(event_id, ticket_number)`, 체크인 순번 유일성 보장.
- 초기화 시 1~300을 보안 난수로 섞은 풀을 저장하거나 남은 번호를 원자적으로 선택하는 동등한 방식. 풀·시드·전체 번호 명단은 참가자에게 공개 금지.
- 행사 할당 행 잠금 → 기존 배정 재확인 → 다음 성공 순번 확정 → 번호 확보 → 체크인·행운권 저장 → 카운터 반영 → commit처럼 실패 없는 절차로 설계한다.
- 동시 도착 순서는 서버 트랜잭션에서 확정된 성공 순서다. 초 단위 화면 도착 시각으로 경쟁시키지 않는다.
- 응답 유실 후 재시도에도 기존 번호 반환.
- 표시는 001~999처럼 최소 3자리로 하고 1000 이상은 잘라내지 않는다.
- 참가자는 자기 번호만 조회 가능. 관리자 운영 명단은 필요 권한에서만 접근.
- 당첨자 추첨 알고리즘/추첨 애니메이션/경품 관리 자체는 이번 필수 범위가 아니다. 번호 발급과 조회부터 완성한다.

## F. 참가자 정보 구조

하단 고정 탭 4개: `내 패스` / `일정·경기` / `안내 지도` / `채팅`.

### 내 패스

- 행사명·날짜, 환영 이름, `3조` 같은 조 배지, 큼직한 `행운권 087`.
- 사번 전체 노출 대신 필요 시 마스킹. 화면 공유 시 최소 정보만 보이게 한다.
- `행운권 크게 보기`: 야외에서 번호를 보여주기 쉬운 큰 글씨, 닫기 쉬운 전체 화면.
- 내 조 자리 위치 바로가기.
- 최신 공지·중요 공지.
- 현재/다음 프로그램, 마지막 갱신 표시.
- 내 조의 첫 대진·선수 준비 안내. 미확정 경기 순위나 자동 대진 결과를 만들어내지 않는다.
- 서버가 admin/owner임을 확인한 계정만 하단에 `관리자 화면` CTA. 탭바·모바일 안전영역과 겹치지 않도록 배치.

### 일정·경기

- 시간대별 간결한 카드, 현재/다음 강조, 종료 접기.
- 메인 4개 경기 설명을 접었다 펼치기. 참가인원·순서·기본 방법·대진표.
- 참가자 화면에서는 **200/100/50 등 점수값·배점표도 기본적으로 생략**해 점수 비공개 취지를 명확하게 지킨다. 대신 순서·인원·참여 방법 중심.
- 운영자가 공개용 경기 설명을 편집. 원문 전체 복사 노출 금지.
- 지연 시 운영자가 실제 진행 상태와 다음 시작 안내를 수정할 수 있도록 한다.

### 안내 지도

- `내 조 자리`, `화장실`, `운영지원·응급보건실`, `버스`, `주차` 바로가기.
- 지도 썸네일 → 확대 모달, 핀치 확대 가능, 닫기 버튼 고정.
- 하차장과 실제 행사장 구분. 주차 3시간 무료/초과 개인 부담은 원문 안내임을 운영자가 확인 후 공개.
- 귀가 배차는 미정 상태로 두고 관리자가 입력. 연락처·확정 버스시간을 임의 생성하지 않는다.

### 참여 편의 기능 — 필수

1. 행운권 크게 보기.
2. 내 조 좌석 지도 바로가기.
3. 지금/다음 일정 및 일정 변경 공지.
4. 중요 공지 상단 고정, 읽음 상태.
5. 전체/팀 채팅과 미읽음 배지.
6. 운영진에게 도움 요청: `길 안내`, `물품`, `기타`. 본인 요청 상태만 확인하고 관리자만 전체 요청 조회. 긴급상황은 현장 운영지원/보건실로 바로 이동하도록 안내. 상시 실시간 대응을 보장하는 문구 금지.
7. 네트워크 끊김 표시·재연결·실패한 메시지 재전송. 서버 처리 여부 불명인 점수 요청은 무조건 재부여하지 않는다.

위 기능을 먼저 완성한다. 불필요한 SNS·랭킹·배지 수집·미니게임·쇼핑 기능을 추가하지 않는다.

## G. 관리자 점수 관리

### 대시보드

- `참가자 화면으로` 복귀.
- 1~8조 전체 카드: 조 이름·누적 점수·현재 순위, 동점은 공동 순위.
- 기본은 조 번호 순으로 안정된 위치, 별도 `순위순` 전환 제공.
- 모바일 2열, 태블릿 4열, 큰 화면 8개가 잘 보이도록 적응형 레이아웃.
- 최근 로그, 팀/종목/부여자/상태 필터, 조회 및 내보내기.
- 체크인 현황은 점수판과 시각적으로 구분.

### 점수 부여 시나리오

1. 관리자 로그인 → 하단 관리자 버튼 → 대시보드.
2. 예: `3조` 클릭.
3. 종목 선택: `1. 풍선기둥`, `2. 단체줄넘기`, `3. 공 튕기기`, `4. 튜브릴레이`, `이벤트 게임`, `응원점수`.
4. 이벤트 선택 시 풍선 터트리기·이벤트 줄넘기·제기차기·이벤트 튜브릴레이·기타 세부유형을 고를 수 있게 한다. 데이터는 메인 종목과 분리.
5. 스크롤 휠/스크롤 스냅 방식으로 점수 선택. **10~200의 모든 10점 단위** 제공. 예: 10,20,30,40,50,60…100…200. 200/100/50/40/30/20/10은 빠른 선택 칩으로도 제공.
6. 휠은 터치·키보드 접근 가능. 선택값이 중앙에 크게 표시. 처음부터 200점 선택하지 말고 `점수 선택` 상태로 시작.
7. 사유: 메인 종목 순위 등 프리셋 또는 직접 입력. 선택한 종목+프리셋으로 구체적인 최종 사유를 만든다. 이벤트/응원은 구체 사유 필수. 공백뿐인 사유 금지.
8. 확인 요약: `3조 / 단체줄넘기 / +100점 / 2위 / 부여자 김○○`. `3조에 100점 부여` 버튼.
9. 성공 후 확정 합계와 로그를 반영. pending 동안 재클릭 잠금. 서버 확정 전에 성공한 것처럼 표시하지 않는다.

수동 점수 입력 모델이다. 한 조·한 종목에 추가 점수를 여러 번 부여할 수 있다. 실수 방지를 위해 같은 관리자·조·종목·점수·사유가 매우 짧은 시간에 반복될 때 경고하되, 명시적인 별도 부여까지 무조건 차단하지 않는다. 동일 요청 재전송은 idempotency key로 단 한 번 처리한다.

풍선 연합팀은 각 조에 같은 점수를 준다. 기본은 조별 개별 부여로 충분하다. 여러 조 일괄 부여를 추가한다면 각 조 점수·대상·원자적 성공/실패·개별 로그를 명확히 처리해야 한다. 일정 맞추기 위해 필수로 만들지 않는다.

### 점수 로그

행별 정보:
- 부여일시(한국시간), 관리자 이름, 대상 조, 종목/이벤트 세부유형, +점수, 사유, 상태(유효/취소), 고유 기록 ID.
- 유효 항목에 `취소` 버튼.
- 취소 시 취소자·시각·사유 추가. 취소된 행을 삭제하거나 숨기지 말고 취소 배지와 상쇄 내역 표시.
- 원문 사유 수정은 금지. 잘못 입력한 것은 취소 후 새 부여.
- 관리자도 타인의 부여 기록을 취소할 수 있으며 취소 권한·비밀번호를 확인한다.

### 취소 규칙

- 취소 모달에 조·원점수·종목·원부여자·원사유 재표시.
- 취소 사유와 비밀번호 입력. 초기 비밀번호 **1234**.
- 비밀번호는 서버 설정에서 해시 검증하거나 동등한 방법으로 관리. 프론트 상수·소스맵·API 응답에 넣지 않는다. 변경 가능한 서버 환경설정으로 두되 기본값은 요청대로 1234다.
- 비밀번호를 아는 참가자는 취소할 수 없다. 관리자 인증도 필수.
- 틀린 비밀번호는 차감 없음. 시도 제한, 로그에 비밀번호를 남기지 않음.
- 원래 +100이면 정확히 -100 상쇄. 취소할 점수를 사용자가 임의 지정하지 않음.
- 취소 API도 트랜잭션·idempotency·원기록당 유일한 reversal로 중복 차감 방지.
- 두 관리자가 동시에 같은 로그를 취소해도 한 번만 차감.
- 취소된 기록을 다시 취소할 수 없음. 취소를 되돌리는 대신 새 점수 부여로 처리.

### 원장과 합계

권장: 변경 불가능한 `score_awards` + 원기록을 참조하는 `score_reversals` 원장. 합계는 유효 부여 합산 또는 부여합계-취소합계로 계산. 원점수를 덮어쓰거나 로그 삭제 금지. 캐시 합계가 있다면 동일 트랜잭션으로 갱신하고 원장으로 검증 가능해야 한다. 관리자 새로고침·서버 재시작 뒤에도 동일 합계.

실시간 갱신은 관리자 전용 채널. 참가자에게 보내고 화면에서 숨기는 방식 금지.

## H. 전체·팀 채팅

- 인증 사용자만 이용. 탭 `전체` / `우리 조`.
- 참가자는 전체 채팅과 자기 조 채팅만 읽고 쓸 수 있다. 다른 team_id를 넣은 HTTP·WebSocket·구독 요청 차단.
- 일반 관리자는 전체+자기 팀, 다른 팀 방 열람이 필요하면 명시적인 관리자 조정 화면에서만 감사 가능한 접근. 참가자 일반 경로를 우회시키지 않는다.
- 표시명은 서버 명단 이름+조 배지. 사번 공개 금지. 관리자는 운영진 배지.
- 텍스트 채팅만 우선. 파일 첨부·외부 링크 자동 미리보기·개인 DM은 범위 밖.
- 길이 제한(예: 500자), 빈 내용 금지, XSS escape, 도배 제한, 메시지 idempotency, 서버 시각, 페이지네이션.
- 성공/전송 중/실패 구분. 네트워크 오류 후 재전송 시 중복 없음.
- 자신 메시지 삭제는 삭제 표시 유지. 관리자 숨김·신고 처리 가능.
- 운영 공지는 일반 채팅과 분리해 상단 고정. 점수 이벤트가 채팅에 자동 게시되지 않음.
- 로깅·분석 서비스에 채팅 원문/사번을 무분별하게 전송하지 않는다.
- 읽음은 채널별 마지막 확인 시각/메시지 ID 정도로 구현. 모든 참가자별 상세 읽음 목록은 불필요.

## I. 디자인 디렉션 — “AUTUMN FIELD CLUB”

목표는 야외 운동회용으로 밝고 활동적이면서, 실제 브랜드 디자이너가 만든 모바일 행사 패스처럼 정교한 화면이다. 장난감 같은 유아 체육대회 디자인도, 기업 ERP 같은 작은 표도 피한다. 기본 화면에서 내 조와 행운권이 즉시 읽혀야 한다.

### 시각 체계

- 배경 warm ivory `#F6F4EC`, 본문 ink `#17261E`, primary deep field green `#164A38`, accent lime `#D6EF78`, orange `#F07843`, 경계 `#DCDDD2`.
- 색상값은 출발점. 실제 대비를 측정하고 본문/버튼 WCAG AA 수준으로 조정한다. 주황·연두 위 흰색 작은 글씨 금지.
- 헤드라인은 굵고 선명한 한글 산세리프, 본문은 Pretendard/Noto Sans KR 계열. 폰트 라이선스를 확인하고 적법하게 포함. 외부 폰트가 실패해도 대체 폰트로 유지.
- 행운권 숫자는 tabular numbers, 큼직하게. 예: 내 조 32~40px, 행운권 64~88px, 본문 16px, 보조 13~14px.
- 티켓의 절취선·작은 날짜 스탬프·얇은 운동장 라인 등 소수의 그래픽 모티프를 일관되게 사용.
- 카드 라운드는 16~24px 범위, 얇은 테두리와 제한된 그림자. 모든 카드를 같은 둥근 상자로 늘어놓지 말고 패스·공지·일정의 위계를 구분.
- 불필요한 보라 그라데이션, 과도한 글래스 효과, 네온 글로우, 큰 이모지, 의미 없는 대시보드 그래프, 랜덤 3D 캐릭터, 반복되는 AI식 카피 금지.
- 조별 색은 보조식별용. `3조` 텍스트와 함께 사용하고 색만으로 구별하지 않는다.

### 화면 구성

1. 로그인: 행사 일자/장소 상단, 크고 짧은 제목 `오늘은, 같은 팀.`, 이름·사번 폼, 하단 잔디 운동장 라인 그래픽. 정보 입력이 첫 화면에서 보임.
2. 내 패스: 작은 행사 헤더 → 이름 → 주인공 티켓 카드(조/행운권) → 지금/다음 → 공지. 화면을 장식하는 영웅 이미지 때문에 핵심이 밀리지 않게 한다.
3. 일정: 세로 타임라인과 경기 카드. 길게 펼쳐진 규칙은 기본 접기.
4. 지도: 용도별 짧은 탭과 읽을 수 있는 지도, 전체보기. 작은 이미지에 글씨를 우겨 넣지 않음.
5. 채팅: 충분한 말풍선 대비, 조 배지, 날짜 구분선, 키보드에 가려지지 않는 입력창.
6. 관리자: 같은 브랜드를 유지하되 밀도 높은 점수판. 점수 입력은 모바일 바텀시트, desktop 다이얼로그. 선택된 조·종목이 입력 내내 고정 표시.
7. 로그: 모바일은 카드형, desktop은 표형. 취소 상태도 텍스트로 명확하게.

### 상호작용·접근성

- 최소 터치 목표 44px, 야외 사용을 위해 주요 버튼 48px 이상 권장.
- 모바일 safe-area, 360/390/430px 너비, 태블릿 768px, desktop 1440px 확인.
- 바텀시트 열림/닫힘 포커스 관리, ESC 닫기, 라벨, 오류 연결, 스크린리더 공지.
- 애니메이션은 120~220ms 수준의 짧은 전환. 번호 공개 시 짧은 티켓 전환은 가능하나 매 로그인마다 추첨 애니메이션 재생 금지.
- reduced-motion 지원. 채팅 입력·점수 입력 중 과한 움직임 금지.
- 로딩·빈 화면·권한 없음·오프라인·실패·성공 상태를 모두 디자인한다.
- 오류 카피는 사용자가 다음에 할 행동을 설명. 원시 DB 오류를 그대로 노출하지 않는다.
- 한 페이지 장문 스크롤 대신 탭·요약·바텀시트 활용.

## J. 기술·데이터 설계

기존 프로젝트가 없으면 TypeScript 기반 웹 프레임워크 + PostgreSQL + 서버 API + 적절한 실시간 전송을 기본으로 고려하라. 특정 유료 서비스 가입을 선행조건으로 만들지 않는다. 기술 버전·보안 구현은 작업 당시 공식 문서를 확인한다. Supabase 등 관리형 서비스를 쓰면 세션 연동과 RLS까지 완결하고 서버 전용 키를 클라이언트에 넣지 않는다.

가능한 테이블:
- events: 날짜·공개 안내·설정.
- teams: 행사와 1~8조, 공개용 이름·안내. private score와 분리.
- participants: event_id, employee_id(string), name, team_id, role, active.
- sessions 또는 framework session store.
- checkins: participant, 고유 성공 순번, 시각.
- ticket_assignments / ticket_pool / allocation_state.
- score_categories: 4개 메인+이벤트+응원.
- score_awards: 조·종목·점수·사유·actor·idempotency key·시각.
- score_reversals: 원 award 고유 참조·actor·사유·시각.
- announcements, schedule_items, published_game_info.
- chat_channels, messages, channel_read_state, reports.
- help_requests: 요청자·유형·내용·상태.
- audit_events: 권한/명단/설정 변경. 비밀번호·세션토큰 제외.

DB 제약, 서버 유효성 검증, 권한 검사, 실시간 채널 검증을 각 계층에서 설계한다. 전체 사번 명단은 public 스키마/API의 무인증 조회로 노출하지 않는다. 동명이인은 표시 정책을 정하되 사번을 채팅 표시명으로 사용하지 않는다.

점수는 정수 10~200, 10의 배수만 부여 가능. 취소는 서버가 원기록 값으로 음수 상쇄하며 일반 입력에서 음수·0·임의 소수 허용 금지.

가상의 데모 모드와 실제 운영 모드는 명확히 분리. 실환경에서 자동 가상 참가자 생성·관리자 노출 금지. 초기 실행에 필수 환경변수가 없으면 무엇이 필요한지 설명하고 가짜 성공 응답을 주지 않는다.

오프라인에서는 개인정보·관리자 점수 캐시를 남기지 않는 방향을 우선한다. 정적 지도/공개 안내 캐시는 가능하나 로그인 후 민감 화면의 서비스워커 캐싱은 금지. 로그아웃 시 개인 캐시·메모리 제거. 쓰기 작업 오프라인 큐로 점수를 몰래 재전송하지 않는다.

## K. 필수 테스트·인수 기준

테스트는 실 DB 또는 동등한 트랜잭션 환경을 사용한다. 화면 mock만으로 동시성 통과를 주장하지 않는다.

### 로그인·행운권

- 올바른 쌍 통과, 잘못된 쌍/미등록/비활성 거절.
- 다른 행의 이름+사번 혼합 거절, 동명이인 각각 정확한 계정 연결.
- 000123 앞자리 0 유지.
- 고유 300명 성공 후 번호 집합이 정확히 1~300, 중복 없음.
- 301번째=301, 350번째=350.
- 350명 동시 최초 로그인 후 1~350 유일, 순번 1~300에는 셔플된 번호, 이후는 순번과 동일.
- 동일 참가자 10개 동시 요청에도 번호·체크인 하나.
- 299/300/301 경계 동시 요청, 응답 유실·트랜잭션 실패 후 재시도.
- 비활성화·재업로드·재로그인 후 번호 유지.

### 권한·점수

- participant가 직접 관리자 API·로그 URL·실시간 채널·내보내기 호출 → 403 또는 적절한 거절, 점수 바이트 미반환.
- 참가자의 본인 정보 API에도 score/rank/history 없음.
- 프론트 role/team_id 조작으로 권한 상승 불가.
- 관리자 권한 해제 후 기존 세션·실시간 구독 재검증.
- 200점+50점=250, 50점 기록 취소 후 200.
- 취소 비번 오류 시 합계 변화 없음. 참가자는 1234를 알아도 취소 불가.
- 같은 부여 idempotency key 재시도 → 한 번만 반영.
- 서로 다른 관리자 동시 정상 부여 → 모두 정확히 반영.
- 같은 원기록 동시 취소 → 한 번만 상쇄.
- 15점/0/음수/201점/문자 입력 거절.
- 로그 새로고침·서버 재시작 후 보존, 취소자·원부여자 구분.

### 채팅·UX

- 타 팀 HTTP 조회·구독·메시지 삽입 거절.
- 이름·사번 전체 명단이 채팅 API에 포함되지 않음.
- XSS 문자열 텍스트로 처리, 도배 제한, 재전송 중복 방지.
- 조 변경 후 이전 팀 접근 종료.
- 아이폰 Safari·Android Chrome 기준 반응형/키보드/탭바 겹침 확인.
- 참가자와 관리자 실제 두 세션으로 점수 비공개와 실시간 갱신 검증.
- 명확한 오프라인 표시, 민감한 관리자 화면 캐시 노출 없음.

## L. 결과물과 진행 방식

1. 저장소를 읽고 요구사항·권한·행운권·점수 원장을 짧게 정리한 IMPLEMENTATION_PLAN.md 작성.
2. 로그인/참가자 홈/관리자 점수판/점수 입력 4개 핵심 화면의 일관된 디자인 체계 수립 후 구현.
3. 실제 서버·DB·실시간 기능 연결. 핵심 기능부터 완성하고 부가장식은 후순위.
4. 단계별로 실행·검증하고 필요한 경우 수정. 외부 자격증명이 필요한 부분은 정확한 설정값과 막힌 부분을 분리해 보고.
5. 최종 제공: 전체 소스, DB 마이그레이션, .env.example, 가상 roster_template.csv, 로컬 실행법, 배포 준비 안내, 운영자 매뉴얼, 테스트 결과, 알려진 미완료 사항.
6. 운영자 매뉴얼에는 owner 지정, 명단 가져오기, 관리자 지정, 첫 로그인 번호 정책, 점수 부여·취소, 비밀번호 설정, 공지/일정 수정, 데이터 백업·종료 후 삭제 정책을 포함.
7. 프로그램을 외부에 자동 배포하거나 QR을 만들지 말 것. 운영자가 배포 후 URL을 QR로 제작한다.
8. 모든 데이터 삭제/행운권 리셋 버튼은 기본 UI에 만들지 않는다. 운영 데이터 복구·초기화가 필요하면 백업과 별도의 의도적인 운영 절차로만 수행.
9. 비밀·실제 사번·실명 명단을 Git에 커밋하지 않는다. 테스트자료와 실제자료를 분리한다.
10. 완료 보고는 실제 확인한 기능, 실행한 테스트, 필요한 운영 설정을 구분한다. 테스트 안 한 항목을 검증됐다고 하지 않는다.

행사 요약의 미확정 정보는 편집 가능한 설정과 초안 상태로 처리하고, 그 때문에 전체 개발을 중단하지 말라. 사용자가 제공하지 않은 사번 명단·관리자 명단·전화번호·실제 경품·확정 귀가시간은 만들어내지 말라.
